# 2026-11-01 — session 1 : le serveur masqué par un dossier `ldpy`

## Signalement de Maxime

Dans l'espace de travail `semantic_web_micropython`, un clic sur
« ldpy: not installed » ne faisait rien. Puis, après être passé sur le venv
`ldpy` : « The Linked-Data Python server crashed 5 times in the last 3
minutes ».

## Diagnostic

- Le journal du serveur : `cannot import name '__version__' from 'ldpy'
  (unknown location)`. « unknown location » : un paquet-espace de noms.
- La racine de cet espace de travail contient le dépôt `ldpy/`, sans
  `__init__.py`. `python -m` y met le répertoire courant en tête de
  `sys.path` ; le paquet installé en éditable passe par un crochet
  d'import (`__editable___linked_data_python_*_finder`), consulté après la
  recherche dans `sys.path` : le dossier gagne. Une installation ordinaire,
  dans `site-packages`, ne serait pas masquée (PEP 420 : un paquet régulier
  trouvé plus loin dans `sys.path` l'emporte) — vérifié.
- Le client de langage démarre le serveur dans la racine de l'espace de
  travail ; les sondes, elles, tournaient dans le répertoire de l'hôte
  d'extensions. D'où « prêt », puis cinq plantages.
- « not installed » était juste : l'interpréteur choisi avant n'avait pas
  le paquet. Le clic sans effet **n'est pas reproduit** : dans une instance
  isolée de VS Code 1.143.1, avec la 0.4.1 installée, avec ou sans les
  extensions Python et sans interpréteur choisi, `ldpy.setup` ouvre bien le
  menu et attend qu'on le ferme.

## Fait

- `neutralCwd()` : sonde, test d'import, `pip` et serveur tournent dans le
  dossier de l'extension. Fiche 106 mise à jour en place.
- `test/journeys.js` : un contrôle de plus, qui échoue si l'un de ces
  appels perd son `cwd`, vérifié en retirant le correctif.
- Vérifié de bout en bout dans une instance isolée de VS Code, sur un
  espace de travail qui contient un dossier `ldpy/` et le venv `ldpy` :
  avec la 0.4.1, aucun survol ; avec le correctif, le serveur répond.

## Publication

Sur demande de Maxime (« fais la publier une 0.4.2 »), dans la foulée :
CHANGELOG 0.4.2 (ce correctif, et la grammaire régénérée `af2a6ef` qui
n'était dans aucune version), `npm version patch`, branche puis étiquette
`v0.4.2` poussées séparément. Workflow `Publish extension` vert
(run 41310801282) : « Published MaximeLefrancois.linked-data-python
v0.4.2 » sur le Marketplace et sur Open VSX, `.vsix` attaché à la release.
Juste après, les deux répondaient encore 0.4.1 (indexation ; Open VSX
analyse une version avant de l'activer).

Côté environnement, le venv `ldpy` a été réinstallé en éditable « compat »
(`--config-settings editable_mode=compat`) : le dépôt passe par `sys.path`,
et un paquet régulier y l'emporte sur le dossier `ldpy/` de l'espace de
travail. Effet de bord : `test_probe_en_ligne_de_commande` (dépôt `ldpy`)
échoue quand pytest est lancé via le lien symbolique de l'espace de travail
— il compare deux écritures du même dossier, sans `realpath` ; il passe
depuis `~/dev/github.com/linked-data-python`.
