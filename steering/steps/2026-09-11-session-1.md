# 2026-09-11 — session 1 : l'extension reçoit son propre pilotage

## Objectif

Le même traitement que `ldpy` le même jour : intégration GitHub, fiches de
conception rapatriées, `CLAUDE.md`, remise en cohérence du pilotage.

## Ce qui a été fait

- Deux workflows GitHub : `claude.yml` ne démarre que sur la chaîne
  `@claude` ; `claude-code-review.yml` relit chaque pull request en
  commentaires en ligne, sans jamais pousser. Les deux installent les
  dépendances (`npm ci`) avant d'appeler l'action : sans cela l'agent peut
  regarder le diff mais pas le vérifier, et `test/parity.js` est précisément
  ce qui attrape une grammaire retouchée à la main.
- Les neuf fiches 101–109 déplacées depuis le dépôt de pilotage dans
  `steering/design/`, à plat, index compris.
- Les deux scripts repris de `ldpy/steering/bin/` — même outil, la plage de
  numéros passe à 100–199.
- `CLAUDE.md` à la racine : ce qui distingue ce dépôt s'y trouve en premier
  (la grammaire est générée, le serveur de langage n'est pas ici).

## La fiche 101 : le cas discutable

Le principe posé pour ldpy est « une décision voyage avec le code qu'elle
décide ». La fiche 101 décrit le serveur de langage, dont le code est dans
`ldpy/lsp/` : à la lettre, elle devrait partir dans `ldpy`.

Elle est ici quand même, pour trois raisons : 102 et 107 la citent, et rien
dans ldpy ne la cite sauf une mention dans `ldpy/011` ; c'est l'architecture
dont dépendent les huit autres fiches ; et `pilotage/README.md` pose que les
fiches se citent **par identifiant** (`vscode/103`), pas par chemin —
découper 101 du bloc 101–109 casserait la continuité sans rien gagner.

Un `git mv` suffit à revenir dessus si Maxime tranche autrement.
